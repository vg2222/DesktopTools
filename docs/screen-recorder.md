# Screen recorder (H4)

Open **Capture tools → Screen recorder**. The first visit offers setup followed by a guide; both can be skipped and repeated from Help or Settings → Tools.

Screen recording needs Microsoft Visual C++ x64 Redistributable. Setup checks for it and offers Microsoft's official download page if it is missing. Portable users see the warning as soon as the recorder opens. The Record button explains the unavailable feature without opening a save dialog or loading the native backend. Install the x64 package using Microsoft's installer, then try Record again; restart DesktopTools if Windows still reports missing files. The .NET runtime is already included with DesktopTools.

Choose **Recording source** or click anywhere on the selected-display preview to open the display/window/region picker. Search the list and inspect the preview, then confirm the source. Choosing a source does not start recording. Enable microphone and/or system audio if needed (both default to off), choose quality and target FPS, then start and select a new MP4 filename.

The studio hides during recording and a compact capsule shows the source, elapsed time, pause/resume and stop. The clock follows the recorder's Recording/Paused/Finishing status and displays total hours for long sessions. A minimized source window pauses capture until restored; restoring does not override a manual pause. Closing the selected source ends recording and reports why it stopped. Closing or disabling the recorder and tray Quit request finalization; stopping while the save dialog is open cancels the pending start.

Display changes preserve a valid window source or unchanged display pixel bounds. If the selected display disappears or its bounds change, recording finalizes and clears that source. The source is checked again after choosing the output filename. Delayed preview refresh also checks the current source before capturing.

Quality presets are Economy, Balanced and High. Target FPS choices are 24, 30, 60, 90, 120 and 144 with H.264 encoding. Hardware acceleration is requested by default when available. If recording fails or produces incorrect images, turn off **Hardware acceleration** in Recording quality to use software encoding. This preference is saved on the machine; tool profiles restore quality and FPS without changing the hardware preference. Actual capture/encoding speed depends on the machine; a 144 FPS request does not guarantee 144 unique frames per second. Region coordinates are physical desktop pixels, with even output dimensions.
Output is first written to a unique `.partial.mp4` beside the chosen destination. Success moves it without overwriting any existing file. Failure retains the partial file and shows its path; recovery is **not guaranteed**, because a normal MP4 may be incomplete without successful finalization. Forced process termination or power loss can lose the current recording. Save to a local writable folder with sufficient disk space.

## Backend and prerequisites

[ScreenRecorderLib 7.0.1](https://github.com/sskodje/ScreenRecorderLib), MIT, uses Windows Graphics Capture and Windows Media Foundation. Its full license is included in `docs/licenses/ScreenRecorderLib-LICENSE.txt`. Windows 11 x64 is the supported platform. The .NET runtime is bundled in the portable package, but the native recorder also needs **Microsoft Visual C++ x64 Redistributable**. N/KN editions can require **Media Feature Pack**. DesktopTools does not install either dependency automatically. The backend is accessed only when the recording feature is used.

The microphone and loopback sources use the current default Windows input/output devices. Windows microphone permission and device availability affect recording. Device changes during a recording, protected video, HDR, GPU-driver behavior and screen-sharing capture exclusion can affect output. Recorder controls and the recording HUD are hidden from supported captures by default. Initial setup and **Settings → Privacy** let you change that choice independently; capture methods that ignore Windows exclusion may still show them.

Selected audio endpoints are checked before the save dialog and again before native start, with translated missing-device messages. This is availability preflight, not a microphone-permission or audible-capture guarantee. The studio awaits asynchronous native teardown before releasing its session, keeping the window thread free while preventing a second start during cleanup. The focused recorder lifecycle/preflight check passes; earlier metadata-only rates below are historical.

`--record-state-only` checks the status-driven clock, manual pause/minimize/restore/resume, source revalidation after the save dialog, pending-start cancellation and display-change finalization using owned silent helper captures. Monitor snapshots are simulated without changing desktop settings; this is not a physical hot-unplug or mixed-DPI claim. The HUD check exercises hour layout and control reuse without an actual day-long recording.

Settings/profile persistence also passed. The backend documents the hardware option as enabling hardware encoding when available in its [VideoEncoderOptions declaration](https://github.com/sskodje/ScreenRecorderLib/blob/master/ScreenRecorderLib/Options.h).

`dotnet run --project tests/DesktopTools.IntegrationTests -c Release --no-build -- --recorder-only`

Observed: a silent 320 × 200 monitor region entirely inside a known blue/orange helper window produces MP4 with the expected first/last pixel colors, readable metadata, no audio track, and pause duration excluded. Pause/resume, duplicate stop, second recording, existing-output preservation, and removal of successful staging files pass. The UI test checks five languages × two themes, cancellation of the save dialog and feature disabling. Window-only WGC capture now passes the static blue/orange helper check, including its initial frame. Requested 144 FPS produced lower measured metadata rates on this machine, not proof of 144 unique frames. Fragmented MP4 failed duration probing, so the implementation uses ordinary MP4.

Still **Not tested**: real microphone/system audio, subjective A/V synchronization, hour-long recordings, full-monitor output on each GPU, mixed-DPI/negative-origin region selection by pointer, display disconnection during recording, forced termination recovery, and clean Windows installations missing the optional native prerequisites. Automated silent recording proves no audio compatibility claim. Check these before the public release.
