# Screen recorder (H4)

Open **Capture tools → Screen recorder**. The first visit offers setup followed by a guide; both can be skipped and repeated from Help or Settings → Tools.

Screen recording needs Microsoft Visual C++ x64 Redistributable. Setup checks for it and offers Microsoft's official download page if it is missing. Portable users see the warning as soon as the recorder opens. The Record button explains the unavailable feature without opening a save dialog or loading the native backend. Install the x64 package using Microsoft's installer, then try Record again; restart DesktopTools if Windows still reports missing files. The .NET runtime is already included with DesktopTools.

Choose **Recording source** or click anywhere on the selected-display preview to open the display/window/region picker. Search the list and inspect the preview, then confirm the source. Choosing a source does not start recording. Enable microphone and/or system audio if needed (both default to off), choose quality and target FPS, then start and select a new MP4 filename.

The microphone and system-audio meters show activity on the current default Windows devices. They do not prove the saved file contains sound. Use **Record 5-second test** beside the audio settings, then the adjacent Play action, to check picture and audio before a longer session. The test clip is stored temporarily and DesktopTools deletes it when the recorder closes; close the player before closing the recorder if Windows still has the file open. DesktopTools checks that the chosen destination reports at least 512 MB free before starting a regular recording. After saving, the recorder displays the FPS reported by the MP4 file; repeated frames can still make motion less smooth than that number suggests.

The setup window behaves like a normal desktop window and can sit behind other applications. It hides during recording; a compact always-on-top capsule shows the source, elapsed time, pause/resume and stop. The clock follows the recorder's Recording/Paused/Finishing status and displays total hours for long sessions. A minimized source window pauses capture until restored; restoring does not override a manual pause. Closing the selected source ends recording and reports why it stopped. Closing or disabling the recorder and tray Quit request finalization; stopping while the save dialog is open cancels the pending start.

Display changes preserve a valid window source or unchanged display pixel bounds. If the selected display disappears or its bounds change, recording finalizes and clears that source. The source is checked again after choosing the output filename. Delayed preview refresh also checks the current source before capturing.

Quality presets are Economy, Balanced and High. Target FPS choices are 24, 30, 60, 90, 120 and 144 with H.264 encoding. Hardware acceleration is requested by default when available. If recording fails or produces incorrect images, turn off **Hardware acceleration** in Recording quality to use software encoding; the software encoder repeats frames above 30 FPS, so DesktopTools caps the target at 30 FPS in that mode. This preference is saved on the machine; tool profiles restore quality and FPS without changing the hardware preference. Actual capture/encoding speed depends on the machine; a 144 FPS request does not guarantee 144 unique frames per second. A display or region records at the screen's own refresh rate; a single window is captured through Windows Graphics Capture, which is limited to about 48 FPS.

The video bitrate is derived from resolution and frame rate (Economy 0.04, Balanced 0.07 and High 0.12 bits per pixel per frame, with frame rates above 60 counted at half weight, limited to 4–80 Mbit/s) and uses variable bitrate, so detailed text and fast motion are not starved the way the backend's own quality mode starves them. Region coordinates are physical desktop pixels, with even output dimensions.
Output is first written to a unique `.partial.mp4` beside the chosen destination. Success moves it without overwriting any existing file. Failure retains the partial file and shows its path; recovery is **not guaranteed**, because a normal MP4 may be incomplete without successful finalization. Forced process termination or power loss can lose the current recording. Save to a local writable folder with sufficient disk space.

## Backend and prerequisites

[ScreenRecorderLib 7.0.1](https://github.com/sskodje/ScreenRecorderLib), MIT, uses the Windows Desktop Duplication API for displays and regions, Windows Graphics Capture for single windows, and Windows Media Foundation for encoding. If Desktop Duplication cannot start (for example on some remote or virtual displays) DesktopTools falls back once to Windows Graphics Capture. Backend throttling is switched off when hardware encoding is used, because it caused periodic stalls and lost frames on busy machines. Its full license is included in `docs/licenses/ScreenRecorderLib-LICENSE.txt`. Windows 11 x64 is the primary platform. A native ARM64 build can be produced with `./scripts/publish.ps1 -Runtime win-arm64`; it uses the ARM64 build of the same backend and has **not been run on ARM hardware**. The .NET runtime is bundled in the portable package, but the native recorder also needs **Microsoft Visual C++ x64 Redistributable**. N/KN editions can require **Media Feature Pack**. DesktopTools does not install either dependency automatically. The backend is accessed only when the recording feature is used.

The microphone and loopback sources use the current default Windows input/output devices. Windows microphone permission and device availability affect recording. Device changes during a recording, protected video, HDR, GPU-driver behavior and screen-sharing capture exclusion can affect output. Recorder controls and the recording HUD are hidden from supported captures by default. Initial setup and **Settings → Privacy** let you change that choice independently; capture methods that ignore Windows exclusion may still show them.

## Verification on the development machine

The recording probe (`--record-probe`, see `tests/DesktopTools.IntegrationTests/RecordingProbe.cs`) records a full display while a fixture window paints frame-ID cells, a moving bar, scrolling text and a deterministic noise texture. `scripts/analyze-recording-probe.py` decodes **every** frame of the MP4 and reports unreadable frames, lost and repeated frame IDs, timestamp gaps, text sharpness and compression error against the exact expected pixels. Because the fixture is an ordinary WPF window it paints at roughly 96–122 FPS on the development PC, so these runs show what the recorder keeps of what is painted, not that 144 unique frames per second were rendered.

Final runs of the 1.3 recorder (Desktop Duplication, 144 FPS target, hardware encoding, High quality, microphone-free system audio on), 60 seconds each, on the development PC (Windows 11, one 1920×1080 100 Hz and one 2560×1440 display):

| Display | Delivered | Corrupt frames | Repeated | Gaps over 50 ms | Bitrate | Notes |
| --- | --- | --- | --- | --- | --- | --- |
| 1920×1080 | 99.2 FPS | 0 of 5746 | 3 | 3 (worst 514 ms) | 17.8 Mbit/s | 2.8% of painted frames not captured; audio 2 ms from video length |
| 2560×1440 | 100.0 FPS | 0 of 5875 | 6 | 0 (worst 18 ms) | 11.7 Mbit/s | 0.6% of painted frames not captured; audio 7 ms from video length |

Before the fix the same machine produced ~48 FPS files at a low bitrate when recording through Windows Graphics Capture, and ~30 FPS files when the software encoder was used. A previous three-minute run on the 100 Hz display with audio delivered 105 frames per second with no corrupt frame. Window recordings are still limited to about 48 FPS by Windows Graphics Capture. These are measurements on one machine; other GPUs, drivers and busy systems can still drop frames.

Selected audio endpoints are checked before the save dialog and again before native start, with translated missing-device messages. This is availability preflight, not a microphone-permission or audible-capture guarantee. The studio awaits asynchronous native teardown before releasing its session, keeping the window thread free while preventing a second start during cleanup. The focused recorder lifecycle/preflight check passes; earlier metadata-only rates below are historical.

`--record-state-only` checks the status-driven clock, manual pause/minimize/restore/resume, source revalidation after the save dialog, pending-start cancellation and display-change finalization using owned silent helper captures. Monitor snapshots are simulated without changing desktop settings; this is not a physical hot-unplug or mixed-DPI claim. The HUD check exercises hour layout and control reuse without an actual day-long recording.

The focused `--record-encoding-only` check records two silent 320×200 owned helper clips at target144 with hardware requested and with software forced, then decodes initial/final colors. Both passed; observed metadata rates were94.48 and69.22FPS respectively. These are short-run observations, not a distinct-frame benchmark or proof of the selected native encoder. Settings/profile persistence also passed. The backend documents the hardware option as enabling hardware encoding when available in its [VideoEncoderOptions declaration](https://github.com/sskodje/ScreenRecorderLib/blob/master/ScreenRecorderLib/Options.h).

`dotnet run --project tests/DesktopTools.IntegrationTests -c Release --no-build -- --recorder-only`

Observed: a silent 320 × 200 monitor region entirely inside a known blue/orange helper window produces MP4 with the expected first/last pixel colors, readable metadata, no audio track, and pause duration excluded. Pause/resume, duplicate stop, second recording, existing-output preservation, and removal of successful staging files pass. The UI test checks five languages × two themes, cancellation of the save dialog and feature disabling. Window-only WGC capture now passes the static blue/orange helper check, including its initial frame. The source picker supports window capture; minimized/restored and closed-source lifecycles are tested. Requested 144 FPS produced lower measured metadata rates on this machine, not proof of 144 unique frames. Fragmented MP4 failed duration probing, so the implementation uses ordinary MP4.

Still **Not tested**: real microphone/system audio, subjective A/V synchronization, hour-long recordings, full-monitor output on each GPU, mixed-DPI/negative-origin region selection by pointer, display disconnection during recording, forced termination recovery, and clean Windows installations missing the optional native prerequisites. Automated silent recording proves no audio compatibility claim. Check these before the public release.
