# DesktopTools 1.2.9

Long screen recordings no longer eat more and more memory. This release fixes a leak that could push recording to several gigabytes of RAM, most noticeably when capturing a full monitor during gameplay.

## What was wrong

For every frame it recorded, the screen recorder asked the graphics driver for a brand-new full-size picture buffer. On some systems the driver never gave that memory back, so usage kept climbing for as long as you recorded. One report showed about 8.4 GB in Task Manager after recording a game at 30 FPS with system audio.

## What changed

- The recorder now reuses a small, fixed set of frame buffers (4 to start, 16 at most). A buffer is handed back only after the video encoder has finished with it, so frames are never overwritten while they are still being encoded.
- If the encoder falls behind and every buffer is busy, that frame is skipped. Memory stays flat instead of growing, and audio keeps recording.
- If the encoder holds every buffer for two seconds in a row, the recording stops with an error. You get a clear failure instead of a video that silently freezes.
- Resolution, bitrate, capture method and your chosen frame rate are unchanged.

## Results

Measured as the private memory of the recording process, with hardware encoding and system audio on:

| Recording | Before | After |
| --- | --- | --- |
| 144 FPS target | about 1.9 GiB after 52 seconds and still climbing | about 440 MiB after 90 seconds, flat |
| 30 FPS, detailed moving picture, 6 minutes | not measured | about 451 MiB peak, about 1 MiB growth in the last minute |

The finished videos were decoded frame by frame: no corrupt or out-of-order frames, and about 29.9 distinct frames per second at the 30 FPS setting. The person who reported the problem confirmed that recording works normally and no longer uses excessive RAM.

These are private-byte figures for the recording process, which is not the same number Task Manager's default memory column shows.

## Known limits

- 144 FPS is still a target, not a guarantee; the result depends on your screen, game and hardware.
- Software (non-hardware) encoding still uses more memory than hardware encoding, about 1.5 GiB in the moving-picture test.
- **Not tested:** a real game session, graphics cards other than NVIDIA, 4K, mixed-DPI and multi-monitor setups, HDR, graphics-driver loss, remote-viewer behavior, and Windows ARM64. The memory checks were run by the contributor on a single machine and are not part of GitHub's automated checks.

Thanks to Lunar (@CMf-pixel) for finding the cause and contributing the fix.

## Downloads

- `DesktopTools-1.2.9-win-x64-setup.exe` — per-user installer.
- `DesktopTools-1.2.9-win-x64-portable.zip` — self-contained portable build.
- `SHA256SUMS.txt` — checksums for the x64 installer and portable ZIP.

There is no ARM64 package for this release. Requires Windows 11 x64. Screen recording needs the Microsoft Visual C++ x64 Redistributable and Windows Media Foundation. The installer is unsigned, so Windows SmartScreen may show a warning; verify `SHA256SUMS.txt` against the downloaded files.
